PHASE 3 · BATCH 5 — SEARCH + NOTES + TASKS + MENTIONS + DEDUP · NUATIS RECRUIT

CONTEXT
Batch 4 shipped a working kanban with optimistic drag-drop, real-time SSE updates across recruiter sessions, bulk operations, and a rejection flow with the default 7-reason taxonomy. 67/67 tests passing. The recruiter can now run a job pipeline visually. This batch adds the surfaces that turn a job-by-job tool into a full ATS: hybrid search across all candidates, per-candidate notes with @mentions, recruiter task management, and automatic duplicate detection. After this batch, Phase 3 is structurally complete and we move to Phase 4 (communications: email, SMS, voice).

GOAL
A recruiter can: search "senior python developer in Austin" across the workspace and get ranked results in <500ms; leave a note on a candidate, @mention a teammate, the teammate gets an in-app and email notification; create tasks with due dates that show up in their /tasks inbox; and have the system catch when a duplicate candidate is being created so they merge instead.

       setweight(to_tsvector('english', coalesce(name, '')), 'A') ||

2. Search API endpoint:
   - GET /api/candidates/search?q=...&filters=... returns ranked candidate list.
   - Hybrid scoring: full-text via ts_rank_cd on search_vector + semantic via cosine similarity on embedding (when query is long enough — say >3 words — and embeddings exist; for short queries skip the semantic leg). Combine with weighted rank: 0.6 * normalized_ts_rank + 0.4 * normalized_cosine_sim.
   - Filters supported: stage (across applications), source, tags (deferred — schema doesn't have tags yet, leave a hook), date range on last_activity_at, last_contacted (NULL handling — never-contacted candidates are a valid filter).
   - Cursor pagination, page size 25.
   - Performance target: p95 <500ms on a workspace with 100K candidates. Synthetic-load test in tests/search/perf.test.ts that seeds 100K rows in a beforeAll and asserts the latency. If you can't seed 100K in test setup tractably, seed 10K and assert <100ms instead — document the substitution.
   - Embed the search query via /embed at request time; cache embedded queries by hash for 1h in memory (Redis later).

7. Candidate deduplication:
   - On POST /api/candidates and on POST /api/public/apply (find-or-create path): before insert, run dedup check.
   - Dedup signals (any one matches → flag as duplicate):
     a. Exact email match on emails array (case-insensitive).
     b. Normalized phone match (strip non-digits, last 10 digits) on phones array.
     c. Embedding cosine similarity > 0.92 against any existing candidate in the workspace (only if both candidates have embeddings — skip otherwise).
   - For the public apply flow: silently merge into the existing candidate (current behavior — confirm it's still working).
   - For recruiter-initiated POST /api/candidates: return 409 with the matched candidate(s) details. UI shows a "Possible duplicate detected" modal with side-by-side comparison + "Merge" / "Create anyway" buttons.

TECH CONSTRAINTS
- Tiptap, not Slate, not ProseMirror raw.
- Mentions stored as nodes with data-user-id attribute; mentioned_user_ids extracted server-side from the JSON, not from the client's payload (don't trust client-supplied user-id list — validate against the JSON tree).
- search_vector is a GENERATED column — never written to directly.
- Embedding cosine similarity uses pgvector's <=> operator (cosine distance, where 1 - distance = similarity); threshold 0.92 similarity = 0.08 distance.
- The dedup embedding check only runs when BOTH candidates have non-null embeddings, with the partial HNSW index already in place from Batch 3.
- /tasks inbox uses TanStack Query with 30s refetch on focus (no SSE for tasks — overkill).
- The new app.current_user_id GUC must be set in the same SET LOCAL middleware as workspace_id, both inside the per-request transaction.
