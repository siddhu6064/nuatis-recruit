GOAL
Recruiter on /candidates/[id] clicks Compose → in the modal, a Template
picker dropdown lists workspace templates → selecting one renders
subject + body into the editor with {{candidate.name}}, {{job.title}},
{{recruiter.name}} merge fields resolved against the current
candidate's data → recruiter can edit before sending → on send, the
hydrated text goes through the existing 6A.4 compose path unchanged.

Owner role can CRUD templates in /settings/email-templates. Recruiter
role can use templates but not edit them this batch (per-recruiter

SCOPE — BUILD THIS

1. Schema migration. New table email_templates:
   • id uuid pk
   • workspace_id uuid fk, RLS-scoped (nuatis_app role, NULLIF guard)
   • name text — recruiter-facing label (e.g., "Initial outreach")
   • subject text — may contain merge fields
   • body text — plaintext, may contain merge fields
   • category enum('outreach','screening','interview','offer',
     'rejection','follow_up','other') default 'other'
   • is_archived bool default false
   • created_by uuid fk users
   • created_at, updated_at timestamptz
   Indexes: (workspace_id, is_archived), (workspace_id, category).
   Cross-workspace RLS isolation tests: 2 (insert + read blocked
   across workspaces).

2. Merge-field engine in lib/email/merge-fields.ts. Pure function,
   zero deps:
     interpolate(template: string, ctx: MergeContext): string
   Supported tokens (this batch only — explicit allowlist):
     {{candidate.name}}, {{candidate.firstName}},
     {{candidate.email}}, {{candidate.currentTitle}},
     {{candidate.currentCompany}}, {{candidate.location}},
     {{job.title}}, {{job.location}}, {{job.salaryRange}},
     {{client.name}},
     {{recruiter.name}}, {{recruiter.firstName}},
     {{recruiter.email}}
   Behavior:
   • Token regex: /\{\{\s*([a-z]+\.[a-zA-Z]+)\s*\}\}/g
   • Unknown token → leave the literal {{...}} in place (don't throw;
     don't replace with empty). Surfaces author errors visibly.
   • Missing field on a known token (e.g., candidate has no
     currentCompany) → empty string.
   • candidate.firstName derives from candidate.name (first
     whitespace-split chunk); recruiter.firstName same.
   • job.salaryRange formats as "$min – $max" if both present, "$min+"
     if only min, blank if neither.
   Unit tests cover: every supported token, unknown token preserved,
   missing field empty, escaping (literal "{{" via "\{\{" → leave as
   "{{"), idempotency (interpolating twice = same result).

3. Routes (artifacts/api-server/src/routes/email-templates.ts):
   • GET /api/email-templates — list workspace templates (RLS-scoped).
     Filters: ?category=, ?archived=. Default excludes archived.
   • POST /api/email-templates — Owner-only. Validates name non-empty,
     subject non-empty, body non-empty, category in allowlist.
     created_by = current user.
   • PATCH /api/email-templates/:id — Owner-only. Workspace-scoped via
     RLS. Updates updated_at.
   • DELETE /api/email-templates/:id — Owner-only. Soft delete via
     is_archived=true rather than row delete (preserves
     audit trail; archived templates excluded from picker).
   • Audit actions: template.created, template.updated,
     template.archived. Action keys are reserved by convention only —
     no allowlist enforcement (matches existing 6A.0 pattern).
   • Role enforcement: reuse existing role-guard middleware. Recruiter
     role hitting POST/PATCH/DELETE → 403.

4. Compose-time hydration endpoint:
   POST /api/email-templates/:id/render
   Body: { candidateId: string, jobId?: string }
   Returns: { subject: string, body: string, missingTokens: string[] }
   Server resolves the merge context server-side from DB:
   candidate, job (if jobId provided), client (via job.client_id if
   applicable), recruiter (current user). Calls interpolate(). Returns
   hydrated subject + body. missingTokens lists known tokens that
   resolved to empty (informational; UI can show a soft warning).
   RLS isolation: cannot render a template from another workspace,
   cannot resolve a candidate from another workspace.

5. UI — /settings/email-templates page:
   • Owner-only route guard (recruiters get redirect or 403 page).
   • Table: Name | Category | Last updated | Actions (Edit, Archive).
   • "New template" button → modal with Name, Category dropdown,
     Subject, Body fields. Help text under Body lists supported merge
     fields as a copyable reference.
   • Edit modal same layout, prefilled.
   • Archive button confirms then PATCHes is_archived=true.
   • No template preview-with-sample-data view this batch — defer.

6. UI — Template picker in ComposeEmailModal (artifacts/web):
   • New dropdown above the Subject field labeled "Use template…"
   • Lists workspace templates grouped by category, sorted by
     last-updated within category. Hides archived.
   • Selecting a template calls the /render endpoint with current
     candidateId (and jobId if the candidate detail page has one in
     scope — the candidate-application linkage may not always exist;
     if not, omit jobId and the template's job.* tokens render empty).
   • Subject + body fields populate with hydrated content. Recruiter
     can edit freely after.
   • If missingTokens.length > 0, show a non-blocking inline notice
     above Send: "Some fields couldn't be filled: {{...}}, {{...}}"
   • Picker resets to "—" when modal reopens; never auto-applies a
     template.
   • Reply composer (the existing 6A.3 surface) does NOT get the
     template picker this batch — keep replies as freeform. Defer.
